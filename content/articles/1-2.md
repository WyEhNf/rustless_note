## 输入检查

读到一个合法的词，还只能说明开头这一部分认得出来。**完整输入的检查需要走到结尾**，有些错误恰好要到最后才能发现。

```text
123
/* 这一段注释没有结束
```

第一行可以形成整数 `token`。第二行的注释没有闭合，必须继续读到末尾才能确认。非法字符、写坏的数字和未结束的注释，都属于读词时要处理的问题。只输入 `123` 可以检查词法；它是否是一份完整程序，需要另做语法检查。因此“成功读到第一个词”只能说明前缀可以识别。完整的词法检查还要确认后续内容与输入结束的位置。

词都读完以后，还要说明这次按什么规则检查：是表达式、类型，还是整份程序。不同入口会接受不同的写法。

```text
1 + 2
1 2
&i32
```

按表达式检查第一行，可以把所有词组成加法。第二行先认出 1，后面却多出一个 2；如果立刻宣布成功，就漏掉了错误。第三行适合按类型检查，它表示对 `i32` 的共享引用。换成表达式规则，意义就不同了。选择检查入口，就是先说明“这次想读什么”。读完对应部分后，再确认后面已经到达输入结尾。

词法和语法都通过后，可以继续构造 AST。这里的“通过”只说明结构已经成立，类型等问题还要接着检查。

```rust
fn main() {
    let x = 1 + true;
}
```

函数、块、绑定和加法的写法都完整，所以能形成树。接下来的类型检查会发现加法右侧是 `bool`。若把初值写成 `1 + ;`，缺少右操作数，语法本身就不完整。此时应先保留错误及位置，停止把它当成正常 AST 使用。同一处语法错误可能经过不同处理环节。统一收集错误后再显示，能避免把同一件事重复说好几遍。

## 树的使用

AST 建好后，编译器可以从一个节点继续找到它的孩子。函数检查就是沿着这些连接，逐步走到真正参与计算的表达式。

```rust
fn twice(x: i32) -> i32 {
    x + x
}
```

从函数可以找到函数体，从函数体可以找到尾表达式，从加法可以找到左右两个 `x`。后面就沿着这些连接检查名字与类型。树也保留参数和结果类型，因而检查加法时能知道 `x` 的类型，检查函数体时能知道它应当得到 `i32`。再往后，编译器把已理解的结构变成更便于生成机器代码的形式。这个过程通常叫 `lowering`。它仍需要原先的结构说明先做哪一步。

我们阅读程序结构时，通常不必查看内存里的对象。把树按层次打印出来，就能看到同样的**父子关系**。

```text
加法
  整数 1
  乘法
    整数 2
    整数 3
```

这段文本说明 `1 + 2 * 3` 的右侧是一整棵乘法子树。读者不用展开内存中的每个对象，也能看出优先级。把缩进从两个空格改成四个空格，表达式仍然先算乘法。若乘法变成加法的父节点，才说明结构发生了变化。保存一次打印结果，再与后来的结果比较，可以发现意外的结构变化。类型也可以单独打印，错误消息则另外显示文件、行列和原因。
