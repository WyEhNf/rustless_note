## 语义结果的组成

一个函数体检查完成后，名字、类型、调用目标和访问方式已经分别确定。这些结论需要与 AST 中的具体位置相连，后面的处理才能直接使用，也才能说明一处错误影响到了哪些表达式。

可以先把主要结果分成四组。声明记录保存名字、类别、声明身份和所属关系；表达式记录保存每次使用的类型、位置性质、权限、关联声明与调整；类型记录把源码中的类型写法对应到语义类型；常量记录保存已完成求值的结果。

这些记录会在不同阶段逐步补齐。顶层声明主要在第一遍登记，参数和局部绑定在第二遍加入；常量求值会提前产生部分表达式结果；局部类型标注、转换目标与容器实参又会在第二遍继续解析。

## 树与结果

```rust
fn read(x: &i32) -> i32 { *x }
let b = Box::<i32>::new(3);
let n = read(&b);
```

AST 说明这是一处调用，实参是对 `b` 的借用。语义结果说明名字 `read` 指向哪个函数、调用返回 `i32`，以及实参从 `&Box<i32>` 怎样按规则调整为 `&i32`。后面的处理既需要树中的组合顺序，也需要这些已经确定的含义。

把结果按节点编号放在独立表里，可以保留原树，同时直接找到相关结论。打印文本则选择其中一部分方便阅读；如果一份输出只列声明与表达式，就不能据此判断其他类型或常量记录不存在。

## 错误记录与后续处理

```rust
fn take(x: i32) {}
take(true, missing);
let y = another_missing;
```

这里同时有实参数量、首参类型和两个名字查找问题。发现一个错误后，可以用临时 `Error` 类型继续查看独立内容，减少同一处失败反复引起的消息，也尽量一次指出更多问题。

继续检查时留下的临时记录仍需要结合错误状态理解。全部检查结束后，有错误就停止正常代码生成。每条消息还应利用源码范围说明位置，让读者知道是哪个实参、名字或字段需要修改。

## 完整程序的检查流程

[完整程序](/posts/16.3)延续了开篇的 `N`、`Point` 与 `inc`，再加入方法、局部遮蔽和 `loop`。常量决定数组长度，方法提供元素值，数组元素又成为另一次调用的实参。几条规则由这些使用关系自然接在一起。

重点在于比较不同节点留下什么：名字关联绑定，方法调用关联目标并保存接收者借用，下标得到元素位置，`break` 自身是 `Never`，却把携带类型加入 `loop` 的结果。把这些内容放回同一份程序，前面分开的规则就连起来了。

**检查结果让后续能够直接使用已经确认的关系，AST 则继续说明这些关系发生在怎样的结构中。**

回看一个节点时，既可以沿父子关系找到参与计算的内容，也可以按编号取出已经确定的类型和声明。遇到错误，则保留具体原因和位置，继续查看能够独立检查的部分；这些临时结果始终需要与整份程序的错误状态一起理解。
