## 下标与优化

矩阵放进一维数组后，先要把行列位置对应到下标。下标含义清楚了，才方便比较后面各种访问与计算方式。

```cpp
int a[4] = {1, 2, 3, 4};
int b[4] = {5, 6, 7, 8};
int c00 = a[0] * b[0] + a[1] * b[2]; // 19
int c01 = a[0] * b[1] + a[1] * b[3]; // 22
```

**行主序**把一行连续存放。一般位置写成 `i*n+j`，因此结果项累加 `a[i*n+k] * b[k*n+j]`。原题函数接收 `a`、`b`、`c` 和 `n` 四个参数，`n` 固定为 1024，并要求以头文件形式提供函数。朴素三重循环清楚表达公式，但能否满足性能要求取决于访问与计算方式。这里先把正确的下标含义确定下来。

朴素计算中，`B` 的一列在内存里通常不连续。转置先改变这部分访问方式，再结合分块或向量运算讨论性能。

```cpp
// 转置后，同一列变成连续的一行。
bt[j * n + k] = b[k * n + j];
// AVX2 一组容纳 8 个 32 位整数。
__m256i product = _mm256_mullo_epi32(av, bv);
acc = _mm256_add_epi32(acc, product);
```

原来 `k` 增加时，`B` 以 `n` 为步长读取；转置后 `bt` 连续读取，更有利于利用缓存。原回答用 64×64 小块转置，点积部分则每次处理 16 项，分成两组向量累加后合并。`alignas(32)` 指定对齐，原例加载用非对齐形式，临时数组存储用对齐形式。乘法保留低 32 位，加法另外执行；这段整数计算没有使用浮点 FMA。

分块乘法与 OpenMP 只是讨论过的进一步选择，原代码没有实际加入。缓存命中和加速幅度都需要测量，不能保证自动达到某个性能。

## 计算前提

对话后半段要求给出无注释版本。理解这次改动时，重点是确认计算过程仍然一致，同时把原本依赖的条件另外说明清楚。

```cpp
// 有注释的片段
for (int k = 0; k < n; ++k) {
    sum += a[k] * bt[k]; // 累加当前乘积
}

// 去掉循环内注释后，仍执行相同的累加。
```

这个循环依次读取两行连续元素，计算点积。删去行尾注释不会改变乘法与加法。核对两版时，要看循环起止与步长、转置下标、向量累加以及最后求和是否一致。原无注释版本还删除了一个没有使用的头文件引用，主计算过程保持相同。“无注释”只是一种呈现要求，不代表边界条件和计算前提可以不再说明。

一段代码即使没有注释，也仍然有**使用前提**。尤其是整数范围、固定矩阵大小和向量指令支持，都需要单独核对。

```cpp
long long sum = 0;
for (int k = 0; k < n; ++k) {
    sum += 1LL * a[i * n + k] * b[k * n + j];
}
```

这是一段独立的标量教学例子。用更宽整数累加仍要确认数据范围足够，写回 `int` 时也要确认结果可表示。原 `AVX2` 版本每次走 16 项、转置每块 64 项，固定 1024 能整除；换 `n` 后需要处理尾部。静态临时矩阵限制容量，也不适合不加区分地并发写。`AVX2` 还要求运行环境支持。

向量低 32 位运算不能称为“标准 C++ 有符号溢出语义”，普通有符号溢出没有这个保证。原代码清零 `c` 后又逐项覆盖，清零是否必要也应单独衡量；输入输出是否重叠同样需要约定。
