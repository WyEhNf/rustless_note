## 从使用处找到声明

语义分析面对的是一棵已经建好的树。树中有名字和操作，也有它们的先后与嵌套关系；要继续理解程序，还得让名字找到声明，让每个操作得到相应的类型依据。

```rust
const N: usize = 2;
struct Point { x: i32 }
fn inc(x: i32) -> i32 { x + 1 }
fn main() {
    let p = Point { x: 1 };
    let values: [i32; N] = [p.x; N];
    let answer = inc(values[0]);
}
```

这份程序里，`Point` 决定字段 `x` 的类型，`N` 决定数组长度，`inc` 的签名决定调用要求。这些声明供使用处查找，先在 Pass1 中准备。`p` 和 `values` 则随 `main` 的检查逐条加入局部作用域，随后出现的名字才能找到它们。

若把 `inc` 的定义移到 `main` 后面，调用所需的签名仍然能够提前登记。若把局部 `values` 移到使用它的语句后面，那个使用处却还找不到绑定。全局声明与局部绑定有不同的生效规则，把它们放在不同阶段处理，就能保留这种差别。

## 表达式之间的要求

检查 `inc(values[0])` 时，外层调用要求一个 `i32` 实参。下标先使用 `values` 的数组类型，取出的元素也为 `i32`，于是这个结果满足参数要求。调用本身又得到 `inc` 声明的返回类型，成为 `answer` 的类型。

这条关系既经过 AST 的父子节点，也用到了树外的声明记录。仅看调用的两个孩子，无法知道 `inc` 接收什么；仅看签名，也无法知道当前传入的是哪个数组的元素。两类信息配合后，才能说明这次调用的含义。

```rust
fn main() {
    let n = inc(true); // inc 要求 i32
}
```

这一片段沿用前面的 `inc` 声明。目标依然可以找到，但 `true` 的类型为 `bool`，调用无法匹配。准备好声明只给出了检查依据，具体使用还需要自己满足要求。

## 查找与结果记录

全局登记表保存可以共同查找的声明，局部作用域表保存当前位置可见的绑定。检查完一个表达式后，还要把结论与这一次出现的节点对应起来，例如 `values[0]` 的元素类型和 `inc` 的调用目标。

局部表会在离开块时退出，已经确认的结论仍然有用。因此按名字查声明与按节点保存结果，需要分别安排。节点编号和声明编号正是在这里发挥作用：同一声明可以供多次使用，每次使用又保留自己的结果。

**从名字找到声明，从声明取得要求，再把检查结论记回使用处，语义信息就与这棵树联系起来了。**
