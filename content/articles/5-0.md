## 两遍检查的分工

现在开始讨论语义分析。它拿到 AST 后，主要做两件事：先收集声明并确定声明上的要求，再进入函数体检查表达式。这两遍分别称为 `Pass1` 和 `Pass2`，Pass 可以理解成一个处理阶段。

第一遍要知道程序中有哪些类型、函数和常量，结构体有什么字段，函数接收什么参数并返回什么结果。随后还要求需要的常量值，检查结构体能否有限存放、`derive` 请求的能力是否成立，以及入口 `main` 是否符合要求。第二遍再带着这些信息检查函数体。

```rust
fn main() {
    let n: i32 = later(1);
    printlnInt(n);
}
fn later(x: i32) -> i32 { x + 1 }
```

虽然 `later` 写在 `main` 后面，第一遍仍然可以先登记它的名字和签名。签名说明输入是一个 `i32`，输出也是 `i32`。第二遍读到 `later(1)`，就能根据这个要求检查实参，而无须先执行 `later`。

## 表达式检查的主线

Rust 风格语法中，块、`if` 和 `loop` 都可以参与求值。正常结束的表达式有结果类型，包括表示没有额外数据的 `Unit`；直接 `return` 或持续发散的表达式用 `Never` 表示没有正常结果。`let` 负责绑定，函数声明负责定义，仍需按各自规则处理。

父表达式已经知道需要什么类型时，可以向孩子提出 `expected`，也就是当前期望类型。孩子经过检查后，把实际类型等结论交回去。例子中 `later` 的签名给整数 1 提供 `i32` 期望，调用整体再得到 `i32`，满足 `let` 的标注。

类型相同可以直接配合，部分差异允许通过隐式调整满足要求。例如方法需要共享引用时，调用处可能自动补上借用。这样的操作要按顺序记下来，后面才能知道实际怎样使用接收者。

## 三类记录

贯穿检查过程的记录主要可以先分成三类。全局登记表保存共同可查的声明；局部作用域表保存当前位置可见的参数和绑定；按节点保存的结果则留下每次表达式检查得到的结论。局部表会随块退出，已经确认的结果仍然保留。

`NodeId` 是语法节点的编号，区分源码中的每次出现。`SymbolId` 表示声明身份。同一声明可以被多处使用，所以 `x + x` 中两个 `x` 有不同节点编号，却可能关联同一个声明编号。`owner` 另外说明字段、方法或参数属于谁。

## 声明身份与访问权限

```rust
let mut x = 1;
let y = 2;
x = y;       // 位置可写，类型也符合
y = 3;       // 绑定不可写
(x + y) = 4; // 加法整体无法作为赋值位置
```

这说明仅记结果类型还不够。能定位到存储位置的表达式称为 `place`；能否写入这个位置，还要结合可变性和访问路径中的限制。调用又需要保留具体目标，名字使用需要保留关联声明。

**语义分析既要判断表达式能否这样使用，也要留下它为什么能够这样使用。**

本章先把两遍检查和表达式这条主线串起来，再把几类记录、编号与类型比较放在一起说明。后面的章节会按这个顺序逐步展开，遇到某个具体规则时，也可以回到这里确认它使用和补充的是哪一类信息。
