## 隐式调整

实际类型和 `expected` 完全相同，可以直接匹配；类型有差别时，还要看是否允许适配。后文的 `same` 表示类型相同，`coercible` 表示能够按规则适配。

```rust
fn read(x: &i32) {}
let mut n = 1;
let r = &mut n;
read(r);
```

`r` 是可变引用，`read` 只需要共享引用，可以按规则降低要求。反过来，把 `&i32` 用作 `&mut i32`，则会增加原本没有的写权限。相同类型可以直接匹配；`Never` 可以适配正常结果；部分引用和 `Box` 链可以解引用后重新借用。普通 `i32` 到 `u32` 仍需要显式转换。`Error` 的宽容用于继续检查错误程序，不能作为用户代码合法的依据。

一次适配可能包含好几步。每一步改变了什么，需要按顺序留下来，后面才能正确使用这个表达式。

```rust
fn read(x: &i32) {}
let b = Box::<i32>::new(10);
read(&b);
```

`&b` 先得到 `&Box<i32>`。到达 `&i32` 可以理解为：沿外层引用找到 `Box`，再沿 `Box` 找到 `i32`，最后共享借用这个整数。每一步都要知道操作后的类型。借用写在错误位置，就可能仍然得到对 `Box` 的引用，无法满足目标。常见调整还包括可变引用转共享引用、可变重新借用，以及 `Never` 对应上下文结果。后者说明没有正常值需要实际产生。

**多步调整需要按顺序保留，每一步都从上一步得到的类型继续。**

因此结果记录还需要说明调整从什么类型开始，以及最后满足什么要求。只有最后一个类型，往往看不出中间发生了什么。

```rust
fn read(x: &i32) {}
let b = Box::<i32>::new(10);
read(&b);
```

`&b` 原本是 `&Box<i32>`，调用最终需要 `&i32`。保留原类型与有序调整，就能看清从哪里开始、怎样走到目标。通用检查过程可以尝试附加调整，调用参数、`let`、字段或函数结果等具体位置再确认是否满足要求并报告错误。因此不能只检查“有没有 `expected`”，就假定任何不匹配都在同一个位置立即被报告。需要看当前使用点的完整检查。

## 分支的共同类型

`if` 有两条分支时，需要知道整个 `if` 能给外面提供什么结果。两边类型不同，可以先尝试允许的适配，再判断能否形成共同类型。

```rust
let mut x = 1;
let y = 2;
let r = if flag { &mut x } else { &y };
```

`then` 得到 `&mut i32`，`else` 得到 `&i32`。把共享引用转成可变引用不成立，反方向则可以，因而共同结果取 `&i32`。当前次序先尝试 `else` 适配为 `then`，再尝试 `then` 适配为 `else`。成功的一侧要补上相应调整。若两侧分别是 `i32` 和 `bool`，又没有允许的适配，就无法这样得到共同结果。

如果其中一条分支直接 `return`，它就不会正常走到 `if` 的结束位置。`Never` 表示这种没有正常结果的情况，因此参与合并的方式也不同。

```rust
fn choose(flag: bool) -> i32 {
    if flag { 1 } else { return 2; }
}
```

`then` 正常给出 `i32`。`else` 中 `return` 直接离开函数，所以正常走到 `if` 结束位置的路径只有 `then`，整个 `if` 可以取 `i32`。如果两支都跳走，`if` 也可以是 `Never`。反过来，一个普通整数会正常产生值，无法仅靠类型适配让它变成不返回。`Never` 与 `Error` 也有不同用途：前者表达控制流，后者是错误后继续检查的占位。
