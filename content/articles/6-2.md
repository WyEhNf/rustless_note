## 类型与签名

名字收集好以后，要把字段、常量和函数签名中的类型确定下来。这里既有声明之间的先后依赖，也有一个类型内部从外到内的递归。

```rust
struct Row { data: [i32; Row::N] }
impl Row { const N: usize = 3; }
fn first(row: &Row) -> i32 { row.data[0] }
```

先登记 `Row::N`，字段长度才有名字可查。常量声明类型确定后，再求需要的值，就可以解析 `data`。函数参数 `&Row` 先看外层引用，再找到 `Row`。处理整份声明列表与处理一个嵌套类型，是两种不同粒度的工作。当前顺序先登记关联项，再处理常量声明类型、关联函数签名、结构体能力与字段，最后处理普通函数签名。依赖需要时，常量求值可能提前发生。

进入某个具体类型以后，还要按它的写法继续处理。`Unit` 直接表示没有额外数据的结果；引用继续检查所指类型，内建标量有固定含义。容器、`Self`、用户类型与数组也各自需要不同的信息。

```rust
let a: Box<i32>;
let b: Vec<Bool>;   // 没有名为 Bool 的类型时出错
let c: i32<bool>;   // 错误：i32 不接收类型实参
let d: Point<i32>;  // 当前用户结构体不支持类型参数
```

`Box` 与 `Vec` 要求一个元素类型，因而 `a` 可以确定内部为 `i32`。`b` 中的 `Bool` 需要继续查找，大小写不同不能直接当作 `bool`。`Self` 还需要当前所属类型，离开结构体或 `impl` 上下文就缺少依据。数组需要继续求元素类型和长度。当前类型路径与关联值路径的查找范围不同，不能从多段写法存在就推断通用模块类型查找已经完成。

函数签名也在这一阶段确定。等到第二遍进入函数体时，再把**参数名加入局部作用域**，两步就接起来了。

```rust
fn positive(x: i32) -> bool {
    x > 0
}
```

声明阶段确定 `positive` 接收一个 `i32`，返回 `bool`，并检查参数名是否重复。进入函数体后，才把 `x` 这个名字与 `i32` 及参数声明身份组成局部绑定。于是 `x > 0` 能找到它。结构体字段也类似：先知道字段名对应什么类型，并保留字段声明身份，后面检查字段访问与初始化时直接使用这些信息。

## 声明的使用限制

名字查找解决了“这里指的是谁”。使用这个声明时，还需要满足它规定的要求，例如调用时的参数数量和参数类型。

```rust
fn add(x: i32, y: i32) -> i32 { x + y }
add(1, 2);
add(true, 2); // 类型错误
add(1);       // 数量错误
```

三个调用都能找到 `add`。第一个同时满足**参数个数与类型**；后两个分别违反不同要求。对于方法，还要确认有没有正确提供 `self`。对于内建容器，某个名字被认作候选接口之后，也仍要看最终支持的组合。因此阅读调用规则时，应从“找到了谁”继续走到“按照什么要求使用它”。

同样，声明中的类型已经读出来，也不代表第一遍的工作结束了。常量值、对象大小和 `derive` 仍可能暴露其他问题。

```rust
const N: usize = M;
const M: usize = N;
fn main() {}
```

`N` 与 `M` 都能找到，声明类型也都是 `usize`。但初值相互依赖，仍然无法求得常量结果。类似地，结构体字段名字与类型可查，并不能保证对象大小有限；写了 `derive`，也不能保证字段满足能力要求。这些都属于第一阶段继续完成的检查。通过后，第二阶段才按已经准备好的要求逐个检查函数体。
