**语义解析器对程序第一次扫描做的事情是：收集与注册符号。**

## 全局登记表

在 `Pass1` 中我们要维护的东西叫做全局登记表，这些表在本次分析过程中一直存在，在这一次Pass中逐步建好，存放全局名字以及关联项的规范拼接名字。同一个命名空间中的重复全局定义会被拒绝，局部 `Shadowing` 由 `Pass2` 处理。
```rust
const LIMIT: i32 = 10;
fn first() -> i32 { LIMIT }
fn second() -> i32 { LIMIT }
```

`LIMIT` 只声明一次，两个函数都能查到它。检查完 `first` 后，这条全局记录仍然保留，接着检查 `second` 时继续使用。若在顶层再声明一个同名常量，就要报告重复定义。

## NodeID 与 SymbolID

解析器的输入来自于 `AST`，我们需要登记支持的声明，并在使用时解析命名与路径。在设计中，需要区分 `NodeID` 与 `SymbolID`。

`SymbolID` 是声明在语义下的标签，而 `NodeID` 则是节点在语法结构下的标签。这里直接使用声明节点的 `NodeID` 作为 `SymbolID`。在表达式 `x+x` 中，两个`x`具有不同的 `NodeID`，如果引用同一个声明，就应当有相同的 `SymbolID`。

所以在记录表达式事实的过程中，一个 `NodeID` 至多直接关联一个 `SymbolID`，而一个 `SymbolID` 可以被多个 `NodeID` 引用。
```rust
let x = 1;
let sum = x + x;
```

两个使用处各有自己的 `NodeID`，都找到第一行的同一个声明，因此共享这个声明的 `SymbolID`。加法整体也有节点编号，但它产生的是计算结果，可以没有直接关联的声明。

## 名字分类与保护

在收集的过程中，我们需要保护内建名字，这个概念有一些类似保留字，目的是拒绝相应名字被重新定义或遮蔽。检查声明和局部绑定时，都需要考虑这些受保护的名字。

注册需要进行分类，也就是说类型命名空间与值命名空间之间应该区分。

因为需要注意的是，在词法阶段 `i32` 和`x`都可以是普通的标识符`Identifier`。语法树区分类型位置与表达式位置，语义阶段进一步识别 `i32` 这样的内建类型，并确定`x`引用的具体声明。
```rust
struct Point { x: i32 }
fn Point() {}
const Point: i32 = 1; // 错误：与函数争用值名字
```

按当前规则，结构体名字登记到类型命名空间，函数与常量名字登记到值命名空间。前两行可以分别登记，第三行与函数发生冲突。名字相同，还要继续看它们处在哪一类查找范围中。

## 声明类型解析

登记好名字以后，第二步是解析声明类型。这一步包括以下内容。

- 类型声明的确定，对于嵌套的类型，需要递归解析内部类型；对于 `Self`，需要根据 `owner` 确定对应的结构体。当前范围不支持 `type` 别名语句。

- 明确各个“黑盒”的接口类型，包括 `struct` 的字段类型，以及 `fn` 的输入参数与输出类型。需要特别讨论的是 `impl`。`impl` 本身没有名字，我们需要先暂存 `impl`，再将其成员登记到对应目标的关联表中，并保存 `owner` 关系。

- **常量解析**：这相当于是名称绑定与编译期求值。我们需要展开受支持的常量表达式的依赖关系，检查递归环并确定常量值。由此，可以进一步确定数组等结构的编译期长度。

## 常量与依赖

需要特别说明的：常量解析中对递归环的判断采用 `DFS`，当前实现具有 `Fresh`、`Evaluating`、`Done`、`Failed` 四种状态。解析数组类型时，也可能按需提前触发常量求值。
```rust
const N: usize = M;
const M: usize = 3;
struct Buffer { data: [i32; N] }
```

数组需要长度，于是查到 `N`；`N` 又依赖 `M`，沿着依赖先得到 3，再确定数组长度。若把 `M` 的初值改为 `N`，就会在尚未算完 `N` 时再次遇到它，形成常量依赖环。

**先登记名字，才能沿依赖找到声明；求出值以后，才能把长度确定下来。**

## 有限大小

第三步是类型关联的检查。这里主要处理的是结构体与数组的无限内联递归，注意到结构体和数组的布局需要在编译期确定为有限大小。引用、`Box` 和 `Vec` 能够隔断这种内联包含关系。函数递归调用发生在运行期，因此这里不检查函数是否会无限递归。具体检查的方式也是 `DFS`。
```rust
struct Bad { next: Bad } // 错误：直接包含自身
struct Tree { children: Vec<Tree> }
```

计算 `Bad` 的大小时，又必须放下一个完整的 `Bad`，这样会一直展开。`Tree` 中的 `Vec` 通过间接存储保存元素，能隔断内联包含；空的 `children` 也可以形成一棵具体的叶子树。

## 派生能力

第四步是派生接口的检查，需要确认字段支持相应 `trait`，并检查 `Copy` 对 `Clone`、`Eq` 对 `PartialEq` 的显式依赖。

对于 `Copy`，需要依据字段类型判断：共享引用支持 `Copy`，可变引用、`Box` 和 `Vec` 不支持 `Copy`，数组与结构体还需要递归检查其组成部分。因此，不能仅根据关联图成环就否定 `Copy`。

需要区分的是物理成环与逻辑成环。第三步检查直接内联包含造成的无限大小问题；对于有指针隔断的逻辑递归，还需要按照具体 `trait` 规则检查。
```rust
#[derive(Clone, Copy)]
struct Pair { left: i32, right: i32 }
```

两个字段都支持相应能力，且显式列出了 `Copy` 所依赖的 `Clone`。若把字段改为 `Vec<i32>`，结构大小仍可确定，但 `Copy` 要求就无法满足。有限大小与派生能力要分别检查。

## 入口与结果

最后检查 `main` 函数一定要合法存在，并满足无值参数、无泛型参数、返回 `Unit` 的要求。

第一件事情完成后，我们得到：注册完毕的声明表、函数签名表、各个字段的类型、解析后的类型记录，以及常量的绑定与求值结果。
