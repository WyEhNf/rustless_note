**语义分析器的第二次扫描做的事情是：检查表达式并且记录其事实**

## 函数检查的入口

表达式检查主要发源于对函数的检查，函数是进入可执行代码检查的主要入口。

这部分主要处理以下函数的性质：`scope` 的检查、参数的局部绑定、返回类型的检查以及循环上下文的维护。

## scope 符号表

这一部分会产生 `scope` 符号表，这个符号表随当前 `scope` 进入和退出，负责明确内部可见名字的类型、可变性与 `SymbolID`。
```rust
fn f(x: i32) {
    {
        let x = true;
        let a = x;
    }
    let b = x;
}
```

进入函数时，参数 `x` 加入参数所在的 `scope`；进入内层块后，新的 `x` 加入内层 `scope`。`a` 查到布尔值，退出内层后，`b` 又查到参数。全局登记表仍可共用，局部名字则随当前检查位置变化。

## 参数与接收者

参数和接收者先决定函数体里有哪些可见名字，循环上下文再决定跳转会去哪里。

参数类型在函数签名解析时确定，参数名字与局部 `Binding` 在函数体检查时绑定。尤其需要注意 `self` 的绑定。`self` 是方法中特有的接收者，需要定位其 `owner` 位置。对于 `self` 的处理可以理解为一种 `Desugaring`：把 `&self` 理解为一个名字为 `self`、类型为 `&Owner` 的形参。检查时可以直接建立这个 `Binding`。

## 循环上下文

循环栈需要被特别维护，因为循环嵌套时需要明确 `break`、`continue` 的目标。`break` 退出最近的可用循环，`continue` 进入该循环的下一轮，所以需要显式维护一个栈，记录当前检查位置所处的循环上下文。

循环体要求具有 `Unit` 或 `Never` 类型；整个 `loop` 表达式的结果类型由跳出它的 `break` 携带的值共同确定，这一点需要对齐。

进一步地说，成功通过检查的表达式在编译期都应该有确定的类型。对于分支、循环等多路径结构，其结果类型应当能够统一，并考虑 `Never` 的兼容性。

## expected 与实际类型

接下来对表达式的检查，总体来说讨论了这样一个问题：表达式的 `expected` 与实际推导结果能否对齐。

注意到，在 `AST` 的 `Expr` 层级内部存在进一步的递归，表达式已经通过父子关系组织起来。在语义上，父节点在上下文明确时，会对子节点提出一个期望 `expected`，表示子节点应当返回怎样的 `type`；缺少 `expected` 时，则需要先推导子节点的实际类型。

我们检查的事情就是这个 `expected` 是否与真实情况符合。
```rust
fn take(x: u32) {}
fn main() {
    take(1);
    take(true); // 错误：bool 无法满足 u32
}
```

签名给实参提出 `u32` 的 `expected`。整数 1 没有后缀，可以按这个期望确定类型；`true` 固定为 `bool`，需要保留这个实际结果，再说明它与参数要求不匹配。

当然，这个检查不完全机械，在差异发生时需要考虑是否成立隐式转换。

## 表达式事实表

这个检查除了判断能否匹配，还需维护一张表达式事实表。它用 `NodeID` 找到表达式的事实，描述当前表达式的类型、`place` 属性、可变权限、关联声明以及隐式调整。

需要与之区分的是 `Pass1` 中维护的全局登记表，以及 `Pass2` 中维护的 `scope` 符号表，这些表通过名字查找相应声明或绑定。
```rust
let x: i32 = 1;
let a = x;
let b = x;
```

名字查找让两处 `x` 找到同一声明，表达式事实表则分别保存这两次使用的结果。即使离开当前 `scope`，这些按 `NodeID` 保存的结论仍可供后面使用。

**查找表回答当前能找到谁，表达式事实表留下每个节点已经查明的结果。**

接下来讨论如何进行检查。

## 基础值与聚合值

首先检查基础值与聚合值：

- **字面量**：整数依次依据后缀、`expected`、默认 `i32` 的顺序确定类型，并检查整数范围。布尔值与 `Unit` 具有各自固定的类型。

- **`path`**：首先需要作 `desugar`，将 `Self` 展开。然后一个重要的设计是，在 `Pass1` 中，对于关联路径，我们将拼接名字作为整体登记进哈希表，在这里通过平均O(1)的哈希查询检查它是否存在；路径拼接与字符串哈希还需要处理路径内容。单段名字优先查询局部 `scope`。

- **`array`**：需要检查元素类型与编译期长度。空数组需要 `expected` 提供元素类型，重复数组的次数需要是编译期常量；重复次数大于1时，元素需要支持 `Copy`。

- **`struct`**：重点检查字段命名是否合法，包括未知、重复和缺失字段，并检查每个字段值是否符合声明类型。

## 块、分支与循环

然后检查结构控制部分：

- **`block`**：`block` 本身是表达式，内部包含 `Stmt`，通过循环依次检查 `Stmt`，并根据尾表达式确定结果类型。进入块时压入 `scope`，离开块时弹出。最后一个无分号表达式接收块的 `expected`，普通带分号表达式的值被丢弃；当前实现还对末尾 `Never` 表达式作了处理。

需要强调的是，对于 `let` 语句，**先检查初值，再登记新名字**，这样才能让遮蔽前后的名字按正确顺序生效。在 `let x=x+1` 中，右侧`x`应当查找此前已经可见的声明；没有已有声明时才报告未解析名字。
```rust
let x = 1;
let x = x + 1;
let y = x;
```

第二行的初值先使用第一行的 `x`。初值检查结束后，新绑定才生效，因此第三行查到的是第二行的声明。若先登记新名字，第二行的右侧就会找错对象。

- **`loop`**：没有 `break` 时，循环类型为 `Never`；`break;` 携带 `Unit`。检查时优先选择 `expected`，然后考虑第一个收集到的 `break` 值类型，各个 `break` 需要能够适配到这个结果类型。

- **`if`**：关键在于是否有 `else`。有 `else` 时优先考虑将 `else` 适配为 `then` 的类型，再考虑反方向；当有分支发散时，优先采用另一分支的类型。没有 `else` 时，为了让`cond`为 `false` 的路径也能统一，`then` 需要满足 `Unit` 或 `Never`，整个 `if` 返回 `Unit`。条件本身需要是 `bool`。

- **`while`**：条件需要是 `bool`，循环体要求 `Unit` 或 `Never`，整个 `while` 返回 `Unit`，`break` 不能携带非 `Unit` 结果。检查 `while` 条件时，当前实现暂时隔离外层循环上下文。

- **`break`/`continue`/`return`**：`break` 与 `continue` 需要合法的循环上下文；`break` 登记携带值的类型，`continue` 不贡献循环结果。`return` 按照当前函数返回类型检查携带值。这三类表达式自身都具有 `Never` 类型。

## 运算与写权限

然后检查运算与赋值部分：

- **`unary`**：这里比较特殊的是写权限的检查与多重引用。写权限检查需要确认当前操作数可写，且没有受到 `access_locked` 限制；这个限制来自当前访问路径中的共享引用或容器规则。借用语境下的 `&&` 对应 `&(&...)`，外层引用不可变。显式解引用只接受引用或 `Box`，负号和取反还需要检查操作数类型。

- **`binary`**：需要按运算符检查操作数类型，逻辑运算要求 `bool`，算术与移位等具有各自的整数约束。需要特别注意 `PartialEq`，相等比较依赖这个能力。

- **`assign`**：这个表达式返回 `Unit`。左侧类型给出对右侧的 `expected`；左侧还必须是可写的 `place`，既能定位到存储位置，又允许写入。复合赋值还需要检查对应的标量运算条件。

- **`cast`**：所有转换都需要被显式规定，当前支持整数之间转换，以及 `bool` 到整数的转换。
```rust
let mut x = 1;
let r = &mut x;
let s = &r;
**s = 2; // 错误：访问经过共享引用
```

沿 `s` 访问时，外层共享引用已经限制了写入。里面虽然还带着可变引用，也不能恢复沿这条路径修改整数的权限。最终指向什么类型、是否定位到存储位置、沿途是否允许写入，需要一起看。

## 函数调用

最后检查调用与存储访问：

- **`call`**：这是一件很复杂的事情，主要讨论的是函数签名。

首先需要推导被调用者是否为函数。确定调用以后，需要把被调用者的 `SymbolID` 和调用目标记到表达式事实中。

检查类型泛型的限制，当前范围中不支持除了 `Box` 和 `Vec` 以外的用户类型泛型。

检查内建I/O函数，这是编译器直接认识、在 `Runtime` 中处理输入输出的函数。

确定关联函数的完整签名。对于带 `self` 的关联函数显式调用，还需要把接收者作为参数检查。

至此我们可以进行签名检查：

- 首先校验参数个数是否正确，立即记录错误，并继续下行收集更多错误。

- 提取参数的类型期望。

- 推导实参在该上下文中的实际类型。

- 检查参数的可转换性，以及可变引用参数的访问权限。

检查内置容器 `Box`、`Vec` 的构造函数与关联接口，例如 `new`、`push` 等。注意 `Box` 和 `Vec` 的实现不在这里，这里将它们当作具有特权接口的容器。

## 方法调用

- **`method`**：所谓方法调用，就是给一个具体对象调用方法，例如 `x.foo()`。这个对象称为接收者。

对接收者进行层层解引用，取得用于方法查找的基础类型。

检查器记录先前解引用的动作，再根据方法签名需要追加借用。这两件事情分开做，是因为在解引用时还不知道最终采用哪一种接收者形式。

对于接收者，这里主要处理两类匹配：

- 内置容器的特权方法匹配。

- 自定义结构体的方法匹配。

随后进行函数签名匹配。要求 `&mut self` 的方法需要可写接收者，没有 `self` 的关联函数不能通过点语法调用。
```rust
struct Counter { value: i32 }
impl Counter {
    fn read(&self) -> i32 { self.value }
    fn add(&mut self) { self.value += 1; }
}
fn main() {
    let c = Counter { value: 0 };
    c.read();
    c.add(); // 错误：c 无法提供可写接收者
}
```

两个方法属于同一结构体，接收者要求却不同。`read` 只需要共享借用，`add` 需要可变借用。找到方法以后，还要继续按签名确认接收者权限。

## 字段与下标

- **`field`**：这是对字段访问的检查。`path` 检查关注名字对应哪个声明，`field` 检查关注接收者类型是否具有这个字段，以及访问权限是否成立。

重点在于可变性的穿透：穿过共享引用以后，访问会被锁定；后续遇到可变引用也不能恢复写权限。但不可变绑定保存的 `&mut T`，仍可以提供对 `T` 的可写访问。

- **`index`**：这是对下标的特别讨论，同样要考虑类型匹配与可变性的穿透。下标需要是 `usize`，容器需要是数组或 `Vec`，结果具有元素类型及 `place` 属性。通过不可写 `Vec` 访问元素时，还会附加访问锁定。

## 作用域、类型与权限

以上就是检查的主要对象。

逻辑关系大概可以这样梳理。从 `AST` 的角度来看，`Crate` 包含 `Item`，`Struct`、`Function` 等构成顶层声明单元，然后往下递归：函数包含块表达式，块内部由 `Stmt` 构成，`Stmt` 再包含初始化表达式或普通 `Expr`。

而块本身也是表达式，因此 `Expr` 中还可以嵌套块、分支与循环，形成递归结构。函数调用与方法调用则结合 `Pass1` 确定的签名进行检查。

在分析器中，有几件事情贯穿始终：

- **作用域控制**：用 `scope` 栈维护可见名字，用循环栈维护跳转所属的循环。

- 表达式 `expected` 与实际事实的 `match` 检查。

- **各种权限**：`place` 属性、可写权限与可写性的穿透。

- 解引用与路径展开。

- **错误记录与恢复**：尽量继续检查其他节点；存在错误时，阻止进入正常代码生成。

## 语义结果的组成

然后我们需要明确分析器最后保存了哪些内容：

`Symbols`：由两个阶段共同完成。`Pass1` 登记顶层声明、关联项和字段，`Pass2` 登记参数和局部变量，记录其 `SymbolID`、名字、类别及 `owner` 关系。

`Expressions`：主要在 `Pass2` 的表达式检查过程中确定，也包括 `Pass1` 常量求值产生的表达式事实，记录类型、`place`、权限、关联 `SymbolID`、调用目标与隐式调整。

`Resolved_types`：`Pass1` 解析声明中的类型，`Pass2` 遇到 `let` 类型标注、`cast` 目标和容器类型实参等内容时继续补充，记录类型语法节点 `NodeID` 与语义类型的对应关系。

`Constants`：主要由 `Pass1` 完成依赖解析和求值，最终记录已完成求值的常量 `SymbolID` 与对应的32位值。

这些结果汇总为 `SemanticResult`，与 `AST` 一起交给后续 `lowering`。
